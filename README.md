# Solid Dataspace Manager

The host application for Solid Dataspace: shared login, navigation, onboarding, profiles, access requests/decisions, Data Connection and the Admin Area. Independent applications such as the Data Manager and Semantic Data Catalog remain separate repositories and are embedded as packages or hosted views.

## Start the complete environment

Use the [Solid Dataspace local setup guide](https://github.com/hoelk-f/solid-dataspace/blob/main/LOCAL_DEVELOPMENT.md). It starts the Manager, apps, gateway and worker with compatible routing. PLASMA, Node-RED and semantic search are optional. This is the recommended route for testing complete workflows.

The local development mode includes source overrides for Health App, City Tours and the worker. The server Admin API/controller is not included in that laptop mode. A Manager page alone does not provide worker, Pod, PLASMA or administrative backend services.

## Develop the Manager itself

Use Node 22 or 24. The Manager depends on versioned `@hoelk-f/*` embed packages from GitHub Packages. For a direct source install, add the following to your private npm user configuration and supply an authorized `NPM_TOKEN` in the environment; never commit a token. The central local setup reuses dependencies from published images and avoids this requirement for its supported development mode.

```ini
@hoelk-f:registry=https://npm.pkg.github.com/
//npm.pkg.github.com/:_authToken=${NPM_TOKEN}
```

```sh
npm ci
npm start
```

The React development server normally opens at `http://localhost:3000`. `prestart` generates legal content and runtime configuration. Set app URLs, registry, issuer/provider choices and worker settings for the environment being tested; the checked-in defaults are not a replacement for deployed services.

```sh
CI=true npm test -- --watchAll=false
npm run build
```

Build output is in `build/`. Container deployment uses port 3001. Runtime settings are generated by `scripts/write-runtime-config.js`, and read through `src/config/runtimeConfig.js`; changing an arbitrary `REACT_APP_*` variable after a React bundle was built does not rebuild that bundle.

## Profiles, registries and applications

The managed server deployment has a shared production stack with host-selected profiles and a separate live Test stack. Profiles determine branding, domains, enabled/visible apps, provider choices, registry and administrators. DACE and TimberConnect are profiles, not separate source forks. Test 2 is retired.

Profile YAML belongs to the [orchestration repository](https://github.com/hoelk-f/solid-dataspace/tree/main/config). The compiler and activation logic in `scripts/deployment/` generate runtime settings and routing. `APP_DATASPACE_ID` identifies the configured profile; it is not an access grant or a universal filter for every app. Catalog discovery follows the configured registry. Urban Data Explorer currently has a deliberately curated Stadt-Wuppertal selection, excluding DACE and TimberConnect.

Application visibility does not enforce permissions. Solid Pod ACLs and authenticated backend checks remain authoritative. Existing legacy technical IDs such as `environmental-monitoring` are retained where required by configuration compatibility.

## Admin Area

The Admin Area combines the Statistics Dashboard with profile configuration. It supports application visibility, appearance, catalog/registry settings, configurable catalog metadata profiles (including DACE categories and multiple themes), administrators, sign-in settings, operations and change history.

Profile administrators are configured by exact WebID in `administration.adminWebIds`. Operators have separately configured environment-level capabilities. Statistics read access is a distinct role. Multiple administrators are supported; a profile must retain an administrator.

Configuration changes use draft, validation, review, backup and activation. Domain changes require correct DNS and operator authorization. The controller is a private service with constrained deployment access, not a public shell endpoint. See [admin-service/README.md](admin-service/README.md) for deployment, role boundaries, rollback and testing. The Admin UI cannot provision a new Solid Pod or bypass Pod permissions.

## Access requests and decisions

Dataset requests use Solid inbox notifications and the shared model in `src/accessRequestModel.js`. Owners can approve, deny or revoke access. The decision inbox displays delivered outcomes, while actual readable access is checked against the resource. Revoked access can be requested again. In the catalog, the pending-request action checks an existing request rather than submitting a duplicate.

External readers should not treat a UI badge or an inbox message as proof that a resource can be read: the Solid server enforces access on each request. Dataset metadata may be public while the linked file remains restricted.

## Data Connection

One connection list covers personal HTTP/REST connections, continuous streams, Home Assistant and managed provider imports. Creation starts with the connection type. The editors support scheduling, pause, previews and appropriate per-type run actions. Generic HTTP supports JSON and other media types; streams include SSE, NDJSON, JSON sequences and raw bytes.

Own API connections can store deduplicated observation histories using timestamp/identity fields and configurable retrieval windows. Managed import templates include Wuppertal climate, bicycle, UDSP and other supported public providers. They run in the worker, independently of the browser. The worker keeps credentials sealed; source changes require a successful preview. Existing owner, provider and target restrictions protect collected histories.

See the worker's [README](https://github.com/hoelk-f/solid-data-connection-sync-worker), [import guide](https://github.com/hoelk-f/solid-data-connection-sync-worker/blob/main/IMPORTS.md) and [public data API](https://github.com/hoelk-f/solid-data-connection-sync-worker/blob/main/PUBLIC_DATA_API.md). Shared Test imports stay paused during routine development/deployment. An interval or enabled flag is an operational setting, not something a README update changes.

## Session expiry

The host guards its shared Solid session and the session/fetch bridge used by embedded apps. A confirmed expired session opens a blocking reauthentication dialog. Network failures and HTTP 401/403 alone do not trigger logout. Requests are not automatically replayed.

Reauthentication clears local login/workspace state and returns to the prior internal path, query and fragment. The return target is stored for at most one hour in the current tab; external destinations and OAuth callback parameters are rejected or removed. Existing Pod data, provider sessions and server imports are not deleted.

## Routes, legal content and branding

Standalone and embedded routes are distinct: `/catalog/` versus `/web/catalog`, and `/urban-data-explorer/` versus `/web/urban-data-explorer`. Old Explorer routes redirect with query parameters preserved; legacy API aliases preserve request bodies. A route migration requires the matching application image and configuration activation, not only an image update.

Legal/privacy links open bilingual dialogs. `legal/content.json` is the canonical text; `scripts/build-legal-pages.cjs` generates the dialog module and public compatibility documents. Edit the source, not `src/legalContent.generated.json`.

To check production routing:

```sh
npm run build
npx serve@14.2.6 --config serve.json -l 3301
```

In another terminal:

```sh
npm run check:production-routes -- http://127.0.0.1:3301
```

Use `serve.json`; adding `serve -s` changes rewrite precedence and can break legal-page aliases.

## Releases and attribution

Use the orchestration repository's coordinated versioning workflow when releasing changed embed packages and the Manager together. Admin services have their own image outputs. Preserve operational volumes, secrets and configuration history when updating.
